# 05 技术方案

> 描述个人主页的**技术选型、目录结构、构建与部署、性能与 SEO**。本文档已按**实际实现**更新（项目已上线 GitHub Pages）。

## 1. 技术选型（已确认并落地）

| 项 | 选型 | 说明 |
| --- | --- | --- |
| 前端 | **纯静态 HTML / CSS / 原生 JS** | 无框架、无构建步骤、无 npm 依赖 |
| 样式 | 原生 CSS + CSS 变量 | `:root` 浅色 / `[data-theme="dark"]` 深色 |
| 主题切换 | CSS 变量 + `localStorage` | 记忆上次选择，默认浅色，无闪烁 |
| 字体 | **仅系统字体栈** | 零外部字体请求，规避商业字体授权问题 |
| 图标 / 插画 | **CSS 自绘** | 无图标库；下滚箭头、装饰块均为 CSS 绘制 |
| 脚本兼容性 | ES5 语法 | 不用 `let`/`const`/箭头函数/模板字符串，兼容面最广 |
| 本地后端（开发用） | `server.py` | Python 标准库零依赖，仅本地开发用 |
| 线上后端（生产用） | **Supabase Edge Function** | Deno 运行时；与数据库同平台，密钥存 Supabase Secrets，静态站点零改动 |

### 1.1 数字分身（AI 对话，密钥永不进浏览器）

线上（GitHub Pages）没有自建后端，因此把大模型调用放到 **Supabase Edge Function** 上：
浏览器只请求函数，`DEEPSEEK_API_KEY` 存在 Supabase 的 **Secrets** 里，前端文件里没有任何密钥。

三层降级，任何一层失败都不会让页面报错：

| 顺序 | 运行环境 | 实际路径 | 状态显示 |
| --- | --- | --- | --- |
| 1 | 本地（`file://` / `localhost` / `127.0.0.1`） | 浏览器 → 同源 `POST /api/chat`（`server.py` 读 `.env`） → DeepSeek | ● AI 在线 |
| 1 | 线上（GitHub Pages 等静态托管） | 浏览器 → `POST <chatUrl>`（**Edge Function** 读 Secrets） → DeepSeek | ● AI 在线 |
| 2 | 两组自动互换 | 上述主路径失败时，自动再试另一个（本地会试线上函数，线上会试同源后端） | — |
| 3 | 全部不可用 | `localReply()` 本地关键词回复（`main.js`） | ● 演示模式 |

- **配置项**：`scripts/config.js` 的 `chatUrl`（只放函数地址，不放密钥）。留空即跳过函数、直接走同源后端。
- **接口契约**（前端与两个后端一致）：
  - `POST` body `{ "messages": [{ "role": "user", "content": "…" }] }` → `{ "reply": "…" }`
  - `GET` → `{ "aiEnabled": true, "model": "deepseek-flash" }`（前端据此显示「● AI 在线 / ● 演示模式」）
  - 未配置密钥返回 `503 { fallback: true }`；上游报错返回 `502` —— 前端一律回退演示回复。
- **人格来源**：`SYSTEM_PROMPT` 在 `server.py` 与 `supabase/functions/chat/index.ts` 各存一份，**改动需两处同步**（Deno 函数是独立部署单元，无法 import Python 常量），改完跑 `py .deepworks/tmp/compare_prompts.py` 逐字比对。
  人格含两块：①**陪聊**（默认，可闲聊技术/日常、讲笑话、玩梗、适度自嘲）；②**介绍**（问起本人时只依据公开信息）。幽默有护栏：段子不能冒充成他的真实经历、不拿他人特征开涮；介绍本人时不清楚的一律说「暂时不了解」并引导邮箱/微信，绝不编造。
- **入参保护**：最多 20 条历史、单条 ≤ 4000 字符、请求超时 60s，两处后端规则一致。
- **部署**：见 §4.2（网页粘贴或一条命令）。
- **回退开关**：把 `scripts/config.js` 的 `chatUrl` 置为空字符串并 `git push`，线上立即回到演示模式。

### 1.2 意见反馈（双路径，自动选择）

前端的 `submitFeedback()` 按 `scripts/config.js` 是否存在来判断走哪条路：

| 模式 | 触发条件 | 路径 | 使用场景 |
| --- | --- | --- | --- |
| **A 直连 Supabase** | `config.js` 里填了 `supabaseUrl` + `supabaseKey` | 浏览器 → Supabase REST（`POST /rest/v1/feedback`） | **GitHub Pages 等静态托管**（线上实际使用） |
| **B 同源后端** | 未填 | 浏览器 → `POST /api/feedback` → Supabase | 本地 `py server.py` |

两种模式的关键约定：

- **安全**：数据库开启 RLS，策略只放行匿名 **INSERT**，不放行读取/修改/删除。
  前端用的是 Supabase **publishable / anon 公钥**（该产品本就设计为可放在浏览器里公开使用）；
  即使有人拿到它，也只能往表里写、读不到任何反馈内容。**`service_role` 密钥从未使用、绝不会出现在前端。**
- **防刷**：隐藏蜜罐字段（命中则前端假装成功、一个字节都不发出去）＋ 前后端双重长度校验。
- **校验镜像**：直连模式下前端按服务端同样的规则截断字段（`nickname` ≤50、`contact` ≤120、`category` ≤20、`page_url` ≤500、`user_agent` ≤300），避免被数据库约束打回。
- 建表 SQL：`sql/feedback.sql`（在 Supabase SQL Editor 执行一次）。

> 已实测（`.deepworks/tmp/check_deploy.py`，35 项）：CORS 预检返回 200 且允许 `content-type / apikey / authorization / prefer` 四个请求头；匿名写入已放行（用超长内容故意触发数据库约束 `23514` 验证，**不产生数据**）；`config.js` 与 `.env` 指向同一项目与同一密钥。

### 1.3 对话记录（`dialog` 表，后台可见）

目的：**让本人（站长）在 Supabase 后台看到访客与数字分身的完整问答**，用于了解访客关心什么、以及分身有没有答错。

| 项 | 做法 |
| --- | --- |
| 表结构 | `public.dialog`（`id / session_id / page_url / question / answer / model / latency_ms / source / created_at`），带长度约束与 `created_at` / `session_id` 两个索引 |
| 写入方（线上） | `chat` Edge Function 内的 `recordDialog()`：拿到**真实模型回复**后，用 `EdgeRuntime.waitUntil()` **异步不阻塞**地把这一轮写进 `dialog` |
| 写入方（本地） | `server.py` 的 `record_dialog()`：`/api/chat` 成功返回真实回复后写同一张表 |
| 写入凭据 | 前端/函数用的 **publishable 公钥**（RLS 只放行 INSERT）；**不使用、也不需要 `service_role`** |
| 会话串联 | 前端 `chatSessionId()` 生成 16 位随机串存 `sessionStorage`（同一次访问的多轮共用一个 id）；`chatPageUrl()` 上报 `origin + pathname + hash`，**主动丢掉查询串** |
| 送什么 | `{messages, sessionId, pageUrl}`；函数兼容 `session_id` / `page_url` 驼峰与下划线两种写法 |
| 记什么 | 问题（该轮最后一条 user 消息）、回答、模型名、耗时毫秒、来源（`supabase-edge-function` / `local-backend`）、时间 |
| 不记什么 | 不记 IP、不记 UA、不记指纹、不记联系方式；**演示模式回复不记**（没调模型就没有 `recordDialog` 调用） |
| 失败处理 | 入库失败只 `console.warn` / `[warn]`，**绝不影响访客拿回复**（超时 5s，超时即放弃） |
| 开关 | 函数 Secret `DIALOG_TABLE`（默认 `dialog`）；**设为 `off` 即完全停掉记录**（`none` / `-` / `0` 同义）。本地 `.env` 里同名变量、同样语义。空字符串或非法表名会回退成 `dialog`（不是"关掉"） |

**表已建好**：`sql/dialog.sql` 已在本项目执行（`relrowsecurity = true`，策略 `anon can insert dialog`：`INSERT` → `{anon}`，**没有** SELECT/UPDATE/DELETE 策略）。

> ⚠️ 一个容易误判的点：Supabase 对新建表的默认授权里，`anon` 其实拿到了**表级** `SELECT/UPDATE/DELETE` 权限（`\dp` 看得到）。
> 但**真正拦人的是 RLS**：因为只有一条 INSERT 策略，实测匿名 `GET` → `200 []`、`DELETE`/`PATCH` → `204` 且一行都没动。
> 结论：**不要只看 GRANT 就以为数据泄露了**，也别因为看到 GRANT 就去乱改权限；RLS 才是闸门。

**线上实测全链路证据**（2026-09-24）：headless Edge 打开真实 `index.html` + 真实 `main.js` 发问 →
函数返回真实回复 → 表里出现该轮记录（`source = supabase-edge-function`，`session_id` 16 位随机串、
`page_url` 指向发起页面、`latency_ms` 约 600–900ms、`model = deepseek-flash`）。

### 4.2 线上数字分身部署（Supabase Edge Functions，一次性）

线上与本地共用同一份函数源码 `supabase/functions/chat/index.ts`，只要它部署一次、密钥配好，之后改代码用同样方式重发即可。

**方式一：网页部署（零安装，推荐首次）**

1. 打开 [Supabase Dashboard](https://supabase.com/dashboard/project/fudznxnxtoiaxcxcvfuq/functions) → 左侧 **Edge Functions** → **Create a new function**
2. 函数名必须填 **`chat`**（与 `scripts/config.js` 的 `chatUrl` 对应）
3. 把 `supabase/functions/chat/index.ts` 的**全文**粘贴进去 → **Deploy**
4. 在函数详情里**关闭 `Enforce JWT Verification`**（前端用的是 publishable 公钥，不是 JWT；`supabase/config.toml` 里也已设 `verify_jwt = false`）
5. 配密钥：**Project Settings → Edge Functions → Secrets** → 新增 `DEEPSEEK_API_KEY` = 你的 DeepSeek 密钥（密钥只存服务端，不会出现在仓库或浏览器）
   > ⚠️ **先确认密钥本身可用**：在 https://platform.deepseek.com/ 生成新密钥后，建议先用本地 `py server.py` + 访问 http://localhost:8000 试一轮对话（`.env` 填同一把）——能正常回答说明密钥有效，再把它填进 Supabase Secrets。
   > 若上游返回 `401 Authentication Fails`，说明密钥无效/已撤销（本项目 2026-09-24 的旧密钥即为此状态）；`402 / Insufficient Balance` 则是账户余额不足。
6. 验证：浏览器直接打开 `https://fudznxnxtoiaxcxcvfuq.supabase.co/functions/v1/chat`，应看到 `{"aiEnabled":true,"model":"deepseek-flash","source":"supabase-edge-function"}`

**方式二：命令行部署（可重复，推荐日常更新）**

```powershell
# 1) 生成访问令牌：https://supabase.com/dashboard/account/tokens （只做一次）
#    推荐存成「用户级」环境变量：令牌不经过聊天、不落地到仓库，以后重发布也不用再设
[Environment]::SetEnvironmentVariable('SUPABASE_ACCESS_TOKEN','sbp_xxxxxxxx','User')

# 2) 在仓库根目录执行（自动找/下载 Supabase CLI、写 Secrets、发布函数并自检）
powershell -ExecutionPolicy Bypass -File tools\deploy-chat-function.ps1 -SkipSecrets
```

- 脚本不会把密钥写进任何文件；`-SkipSecrets` 可只发函数不动密钥（**密钥早已在 Supabase Secrets 里，日常重发布就用这个**）。
- 之后每次改了 `supabase/functions/chat/index.ts`，重跑同一条命令即可重新发布。
- ⚠️ **`supabase login` 不能由自动化/后台进程代跑**：它会打印授权链接、然后要求把浏览器上的**验证码输回它自己的终端**（`--no-browser` 也一样），没有终端就会永久挂起。要么用上面的用户级环境变量，要么在**你自己的 PowerShell 窗口**里跑 `tools\bin\supabase.exe login` 并手动输入验证码。
- 若在自动化环境里读到的是「父进程环境块没刷新」的问题：直接读注册表取值即可 —— `$env:SUPABASE_ACCESS_TOKEN = [Environment]::GetEnvironmentVariable('SUPABASE_ACCESS_TOKEN','User')`。
- 发布时 CLI 的进度输出走 stderr，PowerShell 会包成红色 `NativeCommandError`，**那不是失败**；看 `Deployed Functions on project ...` 与脚本自检结果（退出码 0 即成功）。

**发布后确认（前端生效）**

1. 核对 `scripts/config.js` 的 `chatUrl` 与上述函数地址一致（默认已填好）。
2. `git add -A; git commit -m "feat: 线上数字分身接入真实大模型"; git push` → 等 1–2 分钟。
3. 跑 `py .deepworks/tmp/check_deploy.py https://chencu-vinegar.github.io/`：脚本会实测函数健康探测，并**真实调用一次**看是否返回大模型回复。
4. 浏览器打开线上站点，分身状态应显示「● AI 在线」，提问能得到真实回答。

**要退回演示模式**：把 `scripts/config.js` 的 `chatUrl` 改为空字符串并 push；或在 Supabase 侧删除该函数。

## 5. 性能与 SEO

### 5.1 性能（实测）

- 首屏资源总量：HTML 14.2 KB + CSS 19.8 KB + JS 15.9 KB（config 1.4 KB）+ 头像 17.2 KB ≈ **68 KB**。
- **零第三方请求**：无 CDN、无外部字体、无图标库、无分析脚本 —— 这是首屏速度与隐私的最大保障。
- 单页无路由、无框架运行时；`main.js` 用 `defer` 加载，不阻塞渲染。
- 图片指定宽高、头像复用同一文件（首屏与数字分身共用，仅请求一次）。

### 5.2 SEO / 基本标签

- `title`、`meta description`、`viewport`、`lang="zh-CN"`。
- 语义化标签（`header`/`main`/`section`/`footer`）、图片 `alt`。
- 可选后续：`og:` 系列标签（分享卡片）、`JSON-LD` Person 结构化数据。

### 5.3 可访问性

- 对比度达标、键盘可访问、`:focus-visible` 焦点可见、移动端可点按尺寸 ≥44px。
- 装饰性元素（页脚大字姓名、蜜罐字段）用 `aria-hidden` 对读屏器隐藏。
- 表单状态区用 `role="status"` + `aria-live="polite"` 播报。

## 6. 安全与隐私

- **密钥分层（前端一行密钥都没有）**：

  | 密钥 | 存放位置 | 谁看得到 |
  | --- | --- | --- |
  | `DEEPSEEK_API_KEY`（本地开发） | 本机 `.env`（`.gitignore` 已忽略） | 只有 `server.py` |
  | `DEEPSEEK_API_KEY`（线上） | **Supabase Secrets** | 只有 Edge Function 运行时 |
  | Supabase publishable / anon key | `scripts/config.js`（公开） | 任何人（设计如此），受 RLS 限制只能匿名 INSERT |
  | `service_role` 密钥 | **从未使用、永不写入** | —— |

- **函数侧保护**：入参条数与长度上限、60s 超时、CORS 白名单（`ALLOWED_ORIGIN` 可收紧到本站域名）；
  需要更严时设 `SITE_ANON_KEY` Secret，函数会比对请求头 `apikey / Authorization`（`index.ts` 的 `keyAllowed`）。
- **仓库卫生**：`.env` 从未进入 Git 历史（已核查 `git log --all -- .env`）；`.gitignore` 覆盖密钥（`.env`）、工具配置（`.opencode/`、`opencode.jsonc`）、CLI 本地文件（`tools/bin/`、`supabase/.temp/`）、临时素材（`.deepworks/`、`uploads/`）。`check_deploy.py` 会扫描前端脚本与函数源码是否误含真实密钥形态（`sk-` 后接长串）。
- **联系方式**：公开邮箱与微信号，手机号在页面上以「详谈时提供」呈现，避免被爬虫直接抓取。
- **对话记录（`dialog` 表）**：只记「问题 / 回答 / 模型 / 耗时 / 来源 / 会话 id / 页面地址 / 时间」，**不记 IP、不记 UA、不记指纹、不记联系方式**；`page_url` 主动丢掉查询串（避免把别人带参数的链接写进库）；只有真实模型回答才入库，演示模式回复不留痕。数据只有本人登录 Supabase 控制台或持平台令牌才能读（RLS 对匿名只放行 INSERT）。**想停就设 `DIALOG_TABLE=off`**（见 §1.3）。
- **留痕范围提醒**：以上"匿名可用"的两个公钥（`scripts/config.js` 里的 Supabase publishable key）**只能是写入型权限**，任何时候都不要给它 SELECT 策略；`service_role` 密钥在本项目从未使用、也永不写入前端或函数。

## 7. 依赖与维护

- 前端**零依赖**：没有 `package.json`、没有构建产物、没有版本升级负担（页面部分仍是纯静态）。
- 唯一的外部运行时是 Supabase（数据库 + 一个 Edge Function），都可在 Supabase 后台可视化查看/回滚。
- **日常发布流程**：
  1. 改前端 → `git push`（1–2 分钟生效）；
  2. 改分身逻辑（`supabase/functions/chat/index.ts`）→ 跑 `tools/deploy-chat-function.ps1`；
  3. 改分身人格 → `server.py` 与 `index.ts` 的 `SYSTEM_PROMPT` **两处同步**；
  4. 改对话记录（表结构 / 字段 / 开关）→ 改 `sql/dialog.sql` 与两端实现（`server.py` 的 `record_dialog()`、`index.ts` 的 `recordDialog()`），**改完记得重发布函数**，并同步 §1.3 与 `README.md`。
- **不用打开控制台也能查库 / 建表**：用平台令牌打 Management API（`POST /v1/projects/<ref>/database/query`，以 `postgres` 身份执行、绕过 RLS，适合「我要看数据 / 我要执行 DDL」），本项目已封装为 `.deepworks/tmp/run_sql.py`。注意**一次多条语句只返回最后一段结果**，SQL 文件按 `utf-8-sig` 读；给用户日常查看的入口仍是控制台 Table Editor。
- 换 Supabase 项目：改 `scripts/config.js`（前端）+ 重跑 `sql/feedback.sql` 与 `sql/dialog.sql` + 用新 `--project-ref` 重发函数；本地再改 `.env`。
- 回归校验：`.deepworks/tmp/check_layout.py`（版式与选择器）、`.deepworks/tmp/check_deploy.py <URL>`（部署、连通性与线上分身实测）、`.deepworks/tmp/build_resilience_e2e.py`（访客端 6 场景：在线 / 断网自愈 / 老浏览器 / 无 fetch / 密钥失效 / 上报字段）、`.deepworks/tmp/build_persona_e2e.py`（演示模式人格 8 项）、`.deepworks/tmp/dialog_switch_test.py`（对话记录开关）。
